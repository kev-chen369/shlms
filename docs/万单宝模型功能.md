# 万单宝模型功能分析与研发设计

## 1. 文档目的

本文分析万单宝式 CPS 推广平台的业务模型，并结合“惠省生活”现有产品设计、Go 服务和 V2 客户端界面，形成可用于产品评审、领域建模和研发拆解的方案。

本方案借鉴的是“推广位、转链、分享、订单归因、佣金和结算”的业务闭环，不复制第三方品牌、界面、文案或非公开接口。渠道能力应通过京东、美团、淘宝闪购等平台正式授权的联盟接口，或服务商提供的正式开放接口实现。

## 2. 产品定位

万单宝式产品主要服务推广员和团队运营者，核心目标是把分散在多个联盟平台中的推广动作统一管理。惠省生活当前定位更偏向消费者返现和跨平台导购，两者可以共享底层 CPS 能力，但前台角色和业务表达不同。

| 维度 | CPS 推广工具模式 | 惠省生活消费者模式 |
| --- | --- | --- |
| 主要用户 | 推广员、内容创作者、团队运营者 | 普通消费者 |
| 核心动作 | 创建推广位、转链、分享和复盘 | 搜索、比价、领券、购买和返现 |
| 收益对象 | 推广者获得推广佣金 | 消费者获得购物返现 |
| 核心数据 | 推广位、转链量、点击、订单和佣金 | 商品、价格、订单、返现和钱包 |
| 主要后台 | 推广数据、佣金、结算和团队管理 | 渠道、订单归因、返现、钱包和对账 |

推荐在惠省生活中保留消费者客户端，并为获批用户增加独立的“推广中心”。

```text
普通用户客户端
├── 首页
├── 分类与省钱
├── 搜索与比价
├── 返现订单
├── 钱包
└── 我的

推广中心
├── 推广位管理
├── 万能转链
├── 推广活动
├── 分享素材
├── 推广订单
├── 推广收益
└── 结算记录
```

## 3. 核心业务闭环

```text
创建推广位
→ 输入商品或活动链接
→ 识别渠道并解析商品
→ 创建内部 Tracking ID
→ 调用渠道联盟转链
→ 生成推广链接、口令、小程序路径或二维码
→ 分享给用户
→ 用户在第三方平台下单
→ 同步渠道订单
→ 按 Tracking ID 和推广位归因
→ 计算渠道佣金、用户返现和推广奖励
→ 渠道确认并结算
→ 钱包入账、提现和对账
```

该闭环中最重要的不是一次转链，而是确保推广位、推广链接、点击、订单、佣金和钱包流水之间可以追溯。

## 4. 功能模块

### 4.1 身份与权限

- 手机号或微信登录。
- 区分普通用户、推广员、团队管理员、运营人员和审核人员。
- 推广员开通状态包括待申请、待审核、已启用、已停用。
- 推广位、推广链接、订单和收益必须按所属用户或团队隔离。
- 后台审批操作必须记录原因、操作者和版本号。

### 4.2 推广位管理

推广位是流量来源和订单归因的基础。建议按投放场景创建，例如：

- 客户端首页
- 商品详情页
- 微信群
- 朋友圈
- 公众号
- 内容账号
- 单次营销活动

一个内部推广位可以映射多个渠道的外部推广位。

```text
微信群推广
├── 京东：position_id / subUnionId
├── 美团：sid
├── 淘宝：relation_id
└── 拼多多：pid / custom_parameters
```

功能要求：

- 创建、编辑、停用推广位。
- 设置默认推广位。
- 同一所有者下推广位名称唯一。
- 展示各渠道映射和同步状态。
- 禁止删除已产生推广链接或订单的推广位，可改为停用。
- 转链时必须显式选择推广位，或使用用户的默认推广位。

### 4.3 万能转链

用户可以输入商品链接、活动链接、商品 ID、渠道短链接或包含链接的推广文案。系统依次完成：

1. 从输入内容中提取 URL。
2. 安全展开短链接。
3. 校验渠道域名白名单。
4. 识别所属平台。
5. 提取商品或活动标识。
6. 校验用户对推广位的权限。
7. 创建内部 Tracking 记录。
8. 调用渠道适配器生成推广链接。
9. 保存转链结果、有效期和渠道请求标识。
10. 生成可复制或分享的内容。

相同幂等键和相同输入应返回已有结果。相同幂等键对应不同输入时必须返回冲突，不能生成第二条记录。

### 4.4 推广活动

- 按渠道、品类和有效期展示已获批活动。
- 活动数据必须来自渠道接口或运营人员审核录入。
- 未取得渠道权限的活动入口默认关闭。
- 活动页支持选择推广位并生成推广链接。
- 活动下线或优惠失效后，客户端展示明确的过期状态。

### 4.5 分享素材

一次转链可生成以下分享形式：

- 普通推广链接
- 渠道口令
- 完整推广文案
- 二维码
- 商品海报
- 小程序路径或小程序卡片
- 第三方 App Scheme

无论使用哪种分享形式，都必须映射到同一内部 Tracking ID。不能仅分享一个固定的小程序入口，否则无法完成商品、推广位和订单的精确归因。

分享记录建议保存分享类型和业务场景，不保存聊天对象、群成员等不必要的个人信息。

### 4.6 订单同步与归因

渠道订单处理流程：

```text
渠道订单响应
→ 保存脱敏后的原始订单
→ 按渠道和外部订单号幂等去重
→ 映射为统一订单模型
→ 提取渠道子标识或推广位
→ 查找 Tracking 和 PromotionLink
→ 绑定用户、推广员和业务场景
→ 固化佣金规则快照
→ 生成返现或推广奖励记录
→ 发布后续处理事件
```

归因优先级：

1. 渠道返回的精确 Tracking 子标识。
2. 独立渠道推广位。
3. 唯一推广链接映射。
4. 审核通过的漏单申诉证据。

相近时间、相近金额或相似商品只能用于辅助人工审核，不能作为自动发放返现的依据。

订单状态和返现状态必须分开维护：

- 订单状态：已创建、已付款、已确认、已完成、已取消、已退款等。
- 返现状态：预计、待确认、待结算、可提现、已提现、失效或已扣回。

### 4.7 佣金、返现和推广奖励

同一订单可能包含：

- 渠道预估佣金
- 渠道实际佣金
- 用户预计返现
- 用户实际返现
- 推广员奖励
- 一级邀请奖励
- 税费和固定成本
- 平台毛利

示例：

```text
渠道实际佣金：10.00 元
用户实际返现：5.00 元
推广员奖励：1.00 元
一级邀请奖励：0.50 元
平台毛利：3.50 元
```

计算规则在订单创建或归因时形成不可变快照。后续规则调整不得回算历史订单。渠道佣金发生退款或冲正时，应追加反向流水，禁止删除原流水。

### 4.8 钱包、结算和提现

钱包分别展示：

- 预计收益
- 待结算余额
- 可提现余额
- 冻结余额

每次余额变化都必须对应一条不可变钱包流水，并通过业务类型、业务 ID 和账户 ID 保证幂等。

提现流程：

```text
创建申请
→ 校验实名、账户、限额和可用余额
→ 冻结余额
→ 风控检查
→ 审核
→ 支付处理
→ 成功结转或失败解冻
→ 通知和对账
```

禁止提供后台直接修改钱包余额的通用接口。

### 4.9 数据看板

推广员可按日期、渠道和推广位查看：

- 转链次数
- 分享次数
- 点击次数
- 有效订单数
- 付款金额
- 预估佣金
- 实际佣金
- 用户返现
- 推广收益
- 转化率

运营后台还需要展示渠道成功率、订单同步延迟、归因失败数、退款率、提现待办和对账差异。

## 7. 与现有代码的关系

当前项目已经具备以下基础：

- `tracking.Service`：创建 Tracking 并处理幂等冲突。
- `promotion.Service`：编排 Tracking 和渠道转链。
- `channel.PromotionLinker`：定义渠道转链接口。
- `channel/jd.Adapter`：将内部商品和 Tracking 映射为京东请求。
- `PostgresRepository`：Tracking PostgreSQL 仓储雏形。
- `POST /api/v1/promotions/link`：基础推广链接接口。

当前缺口：

- 推广位领域模型及渠道映射。
- 原始链接提取、短链展开和平台识别。
- 推广链接持久化及有效期处理。
- 分享文案、二维码、海报和小程序卡片。
- 分享事件和点击漏斗。
- 渠道订单同步、标准化和精确归因。
- 佣金规则快照、消费者返现和推广奖励。
- 钱包、提现、对账和运营后台。
- 多渠道适配及渠道健康监控。

## 8. 安全和风控

### 8.1 链接安全

- 只允许配置过的渠道域名。
- 短链接展开必须限制重定向次数和超时时间。
- 禁止访问本机、内网地址、云元数据地址和非 HTTP/HTTPS 协议。
- 保存规范化后的原始链接和完整重定向审计信息。
- 外部错误信息必须脱敏并转换为稳定内部错误码。

### 8.2 接口安全

- 转链接口按用户、IP 和推广位限流。
- 同一幂等键不能对应不同请求。
- 推广位只能由所有者或获授权成员使用。
- 渠道密钥使用密钥服务或环境引用，禁止写入 Git、日志和响应。
- 原始渠道报文持久化前必须脱敏或加密。

### 8.3 资金安全

- 退款、取消和风控订单必须生成冲正流水。
- 钱包流水只追加，不允许覆盖和删除。
- 提现提交时先冻结余额，失败后通过流水解冻。
- 大额或高风险提现采用双人审核。
- 渠道结算、内部订单和钱包流水需要周期性对账。

### 8.4 业务边界

- 仅展示来自真实查询结果的价格、优惠和预计收益。
- “预计返现”不得表达为确定到账金额。
- 未获批的平台入口默认关闭。
- 不逆向小程序或调用未经授权的非公开接口。
- 推广奖励建议保持单层、基于真实成交，并由专业人员确认经营主体、税务、广告和分销合规要求。

## 9. 分阶段研发计划

### 阶段一：可验证转链闭环

目标：完成从推广位到可分享推广链接的真实闭环。

- 完成 Tracking PostgreSQL 仓储和并发幂等测试。
- 增加 PromotionPosition 和 ChannelPosition。
- 增加 PromotionLink 持久化。
- 实现链接提取、平台识别和安全校验。
- 接入一个正式京东推广位。
- 支持复制推广链接和分享文案。
- 在 V2 商品详情和跳转确认页接入真实转链结果。

验收路径：

```text
创建推广位
→ 粘贴京东商品链接
→ 生成推广链接
→ 复制并分享
→ 在京东正确打开目标商品或活动
→ 后台可追溯 Tracking 和推广位
```

### 阶段二：订单同步和归因

- 接入京东订单同步。
- 保存脱敏原始订单。
- 实现标准化、去重和状态机。
- 使用 Tracking 子标识精确归因。
- 实现订单列表、详情和漏单申诉。
- 覆盖取消、退款、乱序事件和补同步。

### 阶段三：返现和推广收益

- 固化佣金规则快照。
- 计算消费者返现和推广奖励。
- 建立不可变钱包流水。
- 实现退款冲正、余额冻结和提现。
- 建立渠道、订单、佣金和钱包对账。

### 阶段四：多平台和运营能力

- 按实际授权接入美团、淘宝闪购和拼多多。
- 增加活动中心、二维码和推广海报。
- 增加推广数据看板。
- 增加团队成员、权限和推广员审核。
- 增加渠道健康监控、熔断和恢复机制。

## 10. 第一版范围建议

第一版应包含：

1. 京东单渠道。
2. 推广位管理。
3. 商品链接转链。
4. Tracking ID 和幂等处理。
5. 复制链接和分享文案。
6. 推广链接持久化。
7. 京东订单同步和精确归因。
8. 预估佣金或预计返现展示。
9. 基础订单和转化数据看板。

第一版暂不包含：

- 自动群发或自动私信。
- 多级分销。
- 复杂团队裂变。
- 未经人工审核的自动提现。
- 非官方接口抓取。
- 没有获批权限的平台。
- 用固定比例代替渠道实际结算数据。

## 11. 关键验收标准

- 相同幂等请求只能产生一条 Tracking 和一条逻辑转链记录。
- 每条推广链接可追溯到用户、推广位、渠道和原始商品。
- 分享形式不同但归因标识保持一致。
- 测试订单能够通过渠道子标识精确归因。
- 取消、退款和佣金调整不会直接删除原始数据。
- 预计收益与实际收益分别展示。
- 钱包余额变化都有唯一且不可变的流水。
- 渠道不可用、链接过期、网络失败和权限不足均有明确状态。
- 渠道密钥、用户隐私和原始渠道敏感字段不进入日志或 Git。
- 未获得真实渠道证据前，不宣称业务闭环已经完成。

## 12. 结论

惠省生活应优先复用万单宝式的 CPS 基础设施，而不是直接复制其完整推广员产品。第一目标是跑通“推广位—转链—分享—订单—归因”这条真实链路；第二目标才是佣金、返现、钱包和提现；最后再扩展多平台、推广素材、团队管理和数据运营。

只有真实测试订单能够从渠道回流，并准确关联到 Tracking、推广位和用户，才能证明系统具备可用的 CPS 业务闭环。
